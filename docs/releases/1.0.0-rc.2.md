# Magicite 1.0.0-rc.2 — proposed qualification candidate

Status: **unpublished; publication and current security/release decisions pending**.
The package identity is `1.0.0rc2`; the proposed full-channel release tag is
`v1.0.0-rc.2`. This candidate does not claim full v1 GA or independent RC
qualification. The published limited `preview/v1.0.0-rc.1` at source
`69803044c6d105abb3dc09945515df9169fdb996` remains unchanged. Its prior human
acceptance applies to that preview only and is not RC2 or GA approval.

The candidate includes project install/setup guidance and `magicite init`,
protected calibration admission/loading, grouped evaluation and explicit
comparison budgets, and the protected benchmark workflow. Default routing remains
dense and autonomous mutation remains disabled. These implemented mechanisms do
not establish authentic E2/E3 quality or calibration qualification: admissible
grouped/negative data, independent annotation and a fresh protected final set are
still required; the exposed official test cannot become fresh evidence.

Operational use requires supported Python, explicitly acquired production model
bytes, protected custody enrollment, and separate review of exact artifacts and
calibration evidence before activation. Test custody is not deployment custody.
See [Install](../install.md), [Setup](../setup.md),
[Quick Setup](../quick-setup.md) and the [operator tutorial](../operator-tutorial.md).

Retained evidence has specific boundaries. Current-source local wheel/sdist
probes use isolated installs, hashing and simulated custody. Actual released
0.2.0/0.3.1 producers supplied seven artifacts each for read-only preview and
inactive-copy migration; the migration used a NEW empty-roots test policy and
**SIMULATED_CUSTODY**, with seven pending targets and zero admissions. Historical
full inventory continuity failed when WAL/SHM sidecars appeared; only the
independently accepted observed-now baseline was preserved thereafter.

Selected real Linux custody/recovery cases ran on amd64 CI at source
`4ac12361eddd80388e81671b457c7466096b8a58` and a native arm64 Docker VM at
`2c3ee0ce3ef1452ff424e224a8aec1fd9069f813`, with three distinct UIDs and kernel
peer credentials. These observations do not prove real-custody legacy upgrades,
macOS separate-UID deployment, the complete supported platform/upgrade matrix,
or dedicated E6 production performance. Exact RC2 artifact qualification and CI
must bind the newly committed candidate; earlier runs are not reassigned to it.

The proposed `v1.0.0-rc.2` tag triggers the existing release workflow: it pushes
multi-architecture GHCR images, generates SBOM/provenance attestations and a
keyless signature, and creates a GitHub prerelease with attested wheel/sdist
bytes and a verified manifest. With `PUBLISH_TO_PYPI=true` and the exact trusted
publisher configured, prerelease packages go to TestPyPI; stable tags use PyPI.
Wheel attestation requires the declared OIDC/attestations job permissions.
No publisher configuration, upload, signature or attestation has been performed
by candidate preparation. Prereleases retain the existing informational Trivy
scan while the HIGH/CRITICAL release gate applies to stable tags.

Pending obligations include publisher/OIDC readiness, TestPyPI rehearsal and
fetched-channel/provenance verification, the complete supported distribution
and upgrade matrices, dedicated amd64/arm64 hardware with licensed real corpus
and pinned model/performance evidence, independent RC/operator qualification,
and a current explicit security/release decision. A native-only GitHub preview
would not close the original distribution requirements. No release date or GA
qualification follows from this version change.
